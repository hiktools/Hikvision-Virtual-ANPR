# 06 — Virtual device model

## 1. Concepts

A physical source is the upstream camera stream. A virtual device is the software-managed endpoint presented to a client/NVR. An ANPR event is a recognition record associated with a source and a virtual device.

Do not assume one physical camera must always map to exactly one virtual device. The initial UI can enforce one-to-one mapping, but the domain model should make the relationship explicit.

## 2. Device identity

Each virtual device should have:
- Internal immutable UUID.
- Human-readable configured name.
- Stable virtual serial generated by this project, clearly identifying the software origin.
- Manufacturer/product strings only where required by a tested compatibility profile; do not falsely claim official manufacturer identity.
- Firmware/version string for this software.
- Logical channel ID.
- Enabled/disabled state.
- Source camera reference.
- Compatibility profile.
- Endpoint configuration.
- Authentication configuration.

## 3. API model

Example internal JSON (not a Hikvision wire-format response):

```json
{
  "id": "uuid",
  "name": "Front Driveway ANPR",
  "serial": "VANPR-000001",
  "channel_id": 1,
  "source_id": "source-uuid",
  "profile": "generic-rtsp",
  "enabled": true,
  "anpr_enabled": true
}
```

## 4. Multi-device routing

First prototype: route by explicit port or path, e.g. `/device/{device_id}/...`, and publish RTSP URLs with a stable device path. This avoids the need for multiple IPs during early development.

If the target NVR requires per-IP device addressing, add a network adapter that binds multiple addresses to the same application. Keep device logic independent of the binding strategy.

## 5. Endpoint isolation

Every request must resolve to exactly one virtual device. Enforce:
- Device existence.
- Enabled state.
- Authentication.
- Endpoint capability.
- Channel mapping.
- Request size and timeout limits.

Do not allow a client to use a device ID to access another device's source credentials or event data.

## 6. Capability registry

Store capabilities as explicit booleans/versions supported by implementation and tests, not guessed device claims. Examples:
- `device_info`
- `system_time`
- `snapshot`
- `rtsp_main_stream`
- `rtsp_sub_stream`
- `event_subscription`
- `anpr_event`
- `event_search`
- `plate_image`
- `vehicle_image`

Only advertise a capability after its endpoint and behaviour pass tests.
