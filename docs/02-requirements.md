# 02 — Requirements

Requirements use identifiers so implementation issues and tests can refer to them.

## 1. Functional requirements

### Camera inputs

- `CAM-001`: An administrator can add, edit, disable, and delete a physical camera source.
- `CAM-002`: A source supports RTSP URL, transport preference, credentials, and optional stream selection.
- `CAM-003`: Secrets are stored encrypted or in a dedicated secret store; they must not appear in logs or API responses.
- `CAM-004`: The service reconnects after stream interruption with bounded exponential backoff.
- `CAM-005`: Source health reports connection state, last frame time, codec, resolution, and measured frame rate.
- `CAM-006`: A camera can be configured for passthrough without ANPR processing.

### Virtual devices

- `DEV-001`: A physical source may be mapped to one virtual device.
- `DEV-002`: A virtual device has a stable UUID, configured display name, channel identifier, enabled state, and protocol profile.
- `DEV-003`: Device identity fields must be truthful project identifiers; do not impersonate a real manufacturer's serial number or claim official certification.
- `DEV-004`: Each virtual device exposes only the endpoints enabled by its compatibility profile.
- `DEV-005`: Device configuration is isolated so one camera's failure does not crash other devices.
- `DEV-006`: Device endpoints must expose consistent capabilities and channel information.

### Media

- `MED-001`: The system can ingest supported RTSP streams.
- `MED-002`: The system can forward a source stream without transcoding when codec, packetisation, and NVR compatibility permit.
- `MED-003`: Transcoding is optional and explicitly configured.
- `MED-004`: Main stream and substream are independently configurable.
- `MED-005`: Stream timestamps and clock drift are monitored.
- `MED-006`: RTSP credentials are never included in public stream URLs or logs.

### ANPR

- `ANPR-001`: Detection and OCR are separate pipeline stages.
- `ANPR-002`: Each recognition includes source camera, capture time, plate text, confidence, model versions, and image references.
- `ANPR-003`: Plate text is normalised separately from raw OCR output.
- `ANPR-004`: Country-specific validation is configurable; UK rules are the first profile.
- `ANPR-005`: The system retains uncertainty and must not silently convert low-confidence OCR into a definitive plate.
- `ANPR-006`: Duplicate detections of the same tracked vehicle are grouped according to configurable time and spatial rules.
- `ANPR-007`: Operators can correct a plate, with original OCR retained in the audit history.
- `ANPR-008`: Model inference can be rate-limited independently per camera.
- `ANPR-009`: A camera can be excluded from ANPR while still being proxied.

### Events and NVR delivery

- `EVT-001`: Internal events are independent of any vendor-specific XML representation.
- `EVT-002`: Every event has a stable UUID and idempotency key.
- `EVT-003`: Event images include a plate crop and, where available, a vehicle/context image.
- `EVT-004`: Event delivery attempts and outcomes are recorded.
- `EVT-005`: Delivery is retried safely without creating duplicate internal events.
- `EVT-006`: Vendor-specific payloads are generated by adapters from the canonical event.
- `EVT-007`: Native NVR ANPR support is marked unverified until the target NVR indexes and searches a test event.
- `EVT-008`: Generic alarm delivery and native ANPR indexing must be represented as separate integration capabilities.

### Administration

- `UI-001`: Dashboard shows camera, virtual-device, inference, storage, and NVR integration health.
- `UI-002`: Operators can configure sources and virtual-device mappings.
- `UI-003`: Operators can search internal ANPR events by plate, time range, camera, and confidence.
- `UI-004`: Operators can inspect snapshots and event delivery diagnostics.
- `UI-005`: All configuration changes are audit logged.

## 2. Non-functional requirements

- `NFR-001`: A failed inference worker must not terminate stream proxying.
- `NFR-002`: A failed virtual-device endpoint must not affect other virtual devices.
- `NFR-003`: No default external/cloud processing of video or plates.
- `NFR-004`: Services restart automatically after process failure.
- `NFR-005`: The application provides readiness and liveness checks.
- `NFR-006`: All clocks use NTP and timestamps are stored in UTC.
- `NFR-007`: Resource limits and queue sizes are bounded.
- `NFR-008`: Event retention and image retention are configurable independently.
- `NFR-009`: All network listeners and firewall requirements are documented.
- `NFR-010`: Logs are structured and redact secrets and credentials.
- `NFR-011`: The system supports a measured target of 32 configured virtual devices, while actual concurrent ANPR rate is benchmarked and published.
- `NFR-012`: No unsupported claims of native compatibility, security, or accuracy.

## 3. Acceptance levels

1. **Level A — Video proxy:** NVR can display and record a virtual stream.
2. **Level B — Device compatibility:** NVR accepts and maintains the configured virtual device.
3. **Level C — Generic events:** NVR receives an alarm/event, but native plate search is not proven.
4. **Level D — Native ANPR:** NVR indexes the plate and images and exposes them through its native ANPR search workflow.

Project headline compatibility may only claim Level D after repeatable testing on the exact target model/firmware.
